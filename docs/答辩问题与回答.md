# 毕业设计答辩问题与回答

> 项目：CipherWS 笔记系统（池禾笔记）
>
> 后端：Java 17 + Spring Boot 3.5 + MyBatis + MySQL 8（单体，端口 8084）
>
> 前端：Vue 3 + Vite（开发端口 8002）+ Vue Router + Pinia
>
> 本文用途：答辩前自测、现场被问到时按“结论 → 链路 → 取舍”回答。
>
> 代码路径都以项目根目录 `note/` 为起点；代码块是节选，完整实现以源码为准。

---

## 0. 一分钟项目介绍（建议背下来）

> 这是一个在线笔记系统，支持注册登录、笔记增删改查、回收站、标签、文件夹、AI 总结和管理后台。
>
> 后端最初拆成 user、core、ai、admin 四个微服务，后来合并成一个 Spring Boot 单体：一个进程、一个端口 8084、一个 MySQL 库、一个 jar。合并的原因是项目规模不大，单体能明显降低部署和联调成本；代码仍按 user/core/ai/admin 分包，保留了模块边界。
>
> 前端是 Vue 3 + Vite，开发时跑在 8002，通过 Vite 代理把 `/api` 转到 8084；生产环境由 Nginx 托管静态文件，并把 `/api` 反代到 8084。前后端用统一的 JSON 信封和 JWT 认证协作。

如果老师只给 30 秒，就说上面这段，不要展开细节。

## 1. 架构与选型

### Q1：为什么把微服务改成单体？是不是“退步”？

**结论：不是退步，是按项目规模做的取舍。**

可以这样回答：

- 这个项目只有笔记一个业务域，4 个服务共享同一个 MySQL 库，服务之间没有真正的 RPC 调用；
- 拆成 4 个服务后，要维护 4 个 jar、4 个端口、Nacos、配置和启动脚本，部署成本明显高于收益；
- 合并后仍然按包分模块：`user`、`core`、`ai`、`admin`，依赖方向清晰，未来要拆还能拆；
- 单体更适合毕业设计演示和单机部署，老师现场也更容易看到完整链路。

**如果老师追问“微服务不是更先进吗？”**

> 微服务的价值在独立部署、独立扩容、团队边界。这个项目没有多团队、没有独立扩容需求，强行拆会变成“分布式单体”，反而增加网络调用、配置和故障点。技术选型要看场景，不是越拆越好。

### Q2：单体之后，模块边界怎么保证？

- 代码按包隔离：`org.example.cipherws.note.user/core/ai/admin`；
- 每个包内部仍是 Controller → Service → Mapper 的分层；
- `common` 只放跨模块的基础设施：`Result`、异常、JWT、过滤器、实体；
- `ai` 需要读笔记正文时，通过自己的 `AiMapper` 读，不直接依赖 `core` 的 Service，避免循环依赖；
- 未来拆服务时，把包整体搬走，补一个 HTTP/RPC 契约即可。

可以指向：

- `server/src/main/java/org/example/cipherws/note/NoteApplication.java`
- `server/src/main/java/org/example/cipherws/note/*/controller`
- `server/src/main/java/org/example/cipherws/note/*/service`

### Q3：为什么不用 Nacos 和网关？

**结论：单体不需要服务发现；Nginx 已经承担了入口。**

- Nacos 的核心作用是“服务注册与发现”，单体只有一个实例，没有“发现谁”的问题；
- 网关的核心作用是统一入口、路由、鉴权、限流；当前只有 1 个后端，Nginx 用一条 `location /api/` 就能完成入口和反向代理；
- 少一个 Nacos、少一个网关，就少两个进程、两个端口和两类故障点；
- 如果未来拆成多服务，再把 Nacos + Gateway 加回来，属于架构演进，不是现在必须。

### Q4：端口是怎么规划的？

| 组件 | 端口 | 说明 |
| --- | --- | --- |
| 前端 Vite | 8002 | 开发服务器；生产由 Nginx 443 托管 |
| 后端 `note-app` | 8084 | 唯一后端端口 |
| MySQL | 3306 | 数据库 |

- 浏览器开发时访问 `http://127.0.0.1:8002`；
- 前端请求 `/api/**`，由 Vite/Nginx 转到 `127.0.0.1:8084`；
- 8084 不是给公网直接访问的，生产只暴露 Nginx 的 443。

### Q5：一个请求从浏览器到数据库，完整链路是什么？

先给结论：

```text
浏览器
  → 前端 8002（开发） / Nginx 443（生产）
  → 去掉 /api 前缀
  → 后端 8084
  → Tomcat
  → JwtAuthFilter
  → DispatcherServlet
  → Controller
  → Service
  → Mapper
  → MySQL
  → Result → JSON → 前端
```

展开见第 3 节，那里有逐步说明和配置代码。

## 2. 前端怎么封装

前端不是“每个页面自己写 fetch”，而是分四层收敛：

```text
页面 / 组件
  → api/index.js        业务接口清单
  → api/request.js      统一请求、token、错误、上传
  → fetch / Vite 代理
  → 后端 8084
```

另外还有：

- `stores/user.js`：登录态、用户信息、登录/退出；
- `router/guards.js`：登录守卫、管理员守卫；
- `components/`：按钮、输入框、弹窗、分页等基础组件。

### Q6：请求层怎么封装？为什么不直接在页面里 fetch？

核心文件：`frontend/note/src/api/request.js`

它做了 6 件事：

1. 统一 base URL：`VITE_API_BASE_URL` 为空时走同源；
2. 统一拼 `/api` 前缀；
3. 自动带 `Authorization: Bearer <token>`；
4. 统一序列化 query / JSON body；
5. 统一解析后端信封，失败抛 `ApiError`；
6. 单独封装 `upload()`，处理 `multipart/form-data`。

关键代码：

```js
// frontend/note/src/api/request.js（节选）
const BASE = String(import.meta.env.VITE_API_BASE_URL || '')
const API_PREFIX = '/api'
export const TOKEN_KEY = 'note_token'

export function getToken() {
  try {
    return localStorage.getItem(TOKEN_KEY) || ''
  } catch {
    return ''
  }
}

function authHeader() {
  return getToken() ? { Authorization: `Bearer ${getToken()}` } : {}
}

export async function request(path, { method = 'GET', params, body } = {}) {
  const cleanParams = {}
  if (params) {
    for (const [k, v] of Object.entries(params)) {
      if (v !== undefined && v !== null && v !== '') cleanParams[k] = v
    }
  }

  const qs = new URLSearchParams(cleanParams).toString()
  const url = `${BASE}${API_PREFIX}${path}${qs ? `?${qs}` : ''}`

  let res
  try {
    res = await fetch(url, {
      method,
      headers: { 'Content-Type': 'application/json', ...authHeader() },
      body: body === undefined ? undefined : JSON.stringify(body)
    })
  } catch {
    throw new ApiError('网络请求失败，请检查连接')
  }
  return parseResponse(res)
}
```

统一解析响应：

```js
async function parseResponse(res) {
  let json
  try {
    json = await res.json()
  } catch {
    throw new ApiError(`响应不是合法 JSON（HTTP ${res.status}）`)
  }
  if (!res.ok || json.success !== true) {
    throw new ApiError(json.errMessage || `请求失败（HTTP ${res.status}）`, res.status)
  }
  return { data: json.data, total: json.total }
}
```

**答辩时可以强调：**

> 页面只关心“拿到 data 或捕获 ApiError”，不需要重复判断 HTTP 状态、`success`、`errMessage`。这样接口一多，代码不会散。

### Q7：API 层怎么组织？

核心文件：`frontend/note/src/api/index.js`

按业务域分组，页面只 import 对应的 API：

```js
// frontend/note/src/api/index.js（节选）
export const authApi = {
  register: (body) => request('/auth/register', { method: 'POST', body }),
  login: (body) => request('/auth/login', { method: 'POST', body }),
  logout: () => request('/auth/logout', { method: 'POST' }),
  sendCode: (email, purpose = 'reset') =>
    request('/auth/send-code', { method: 'POST', body: { email, purpose } }),
  resetPassword: (body) => request('/auth/reset-password', { method: 'POST', body })
}

export const noteApi = {
  list: (params) => request('/notes', { params }),
  detail: (id) => request(`/notes/${id}`),
  create: (body) => request('/notes', { method: 'POST', body }),
  update: (id, body) => request(`/notes/${id}`, { method: 'PUT', body }),
  remove: (id, hard = false) => request(`/notes/${id}`, { method: 'DELETE', params: { hard } }),
  restore: (id) => request(`/notes/${id}/restore`, { method: 'POST' })
}
```

这样做的优点：

- 页面不写 URL，接口改了只改 `api/index.js`；
- 请求方法、参数位置（query/body）集中可见；
- 和后端 Controller 一一对应，联调时容易对表。

### Q8：登录态、路由和状态怎么封装？

登录态用 Pinia：

- `stores/user.js` 保存 `token`、`userInfo`；
- 登录成功：`setToken(data.token)` + `setUserInfo(data.user)`；
- 刷新页面：`token` 从 `localStorage` 恢复，路由守卫里调 `fetchUserInfo()` 补用户信息；
- 退出：调 `logout()` 清 token，再清空用户信息。

路由守卫：`router/guards.js`

```js
// frontend/note/src/router/guards.js（节选）
const WHITE_LIST = ['/login', '/register', '/forgot-password']

router.beforeEach(async (to) => {
  const userStore = useUserStore()

  if (to.meta.guestOnly && userStore.isLogin) return { path: '/' }
  if (WHITE_LIST.includes(to.path) || to.meta.guestOnly) return true

  if (!userStore.isLogin) {
    return { path: '/login', query: { redirect: to.fullPath } }
  }

  if (!userStore.userInfo) {
    try {
      await userStore.fetchUserInfo()
    } catch {
      await userStore.logout()
      return { path: '/login', query: { redirect: to.fullPath } }
    }
  }

  const roles = to.meta.roles
  if (Array.isArray(roles) && roles.length && !roles.includes(userStore.userInfo?.role)) {
    return { path: '/' }
  }

  return true
})
```

**要强调：前端守卫只是体验层，真正的权限在后端。**

### Q9：组件怎么封装？

- `components/AppButton.vue`、`AppField.vue`、`AppModal.vue`、`AppPager.vue` 等基础组件；
- `layouts/AuthLayout.vue`、`MainLayout.vue` 负责页面骨架；
- `stores/toast.js` 统一提示；
- 页面只组合组件和 API，不重复写按钮样式、分页逻辑、弹窗遮罩。

### Q10：为什么不用 axios？

**结论：当前需求用原生 fetch 足够，少一个依赖。**

- 只需要 GET/POST/PUT/DELETE、JSON、multipart、Bearer token；
- `fetch` 是浏览器标准，Vite 下无需额外配置；
- 统一封装后，页面并不会直接接触 fetch；
- 如果以后需要请求取消、拦截器、自动重试，再引入 axios 也不迟。

**不要答“axios 不好”**，要说“当前规模下没必要”。

### Q11：前端怎么知道后端地址？

- 开发：`VITE_API_BASE_URL` 留空，走同源 `/api`，由 Vite 代理到 8084；
- 生产：同样留空，由 Nginx 同源反代；
- 只有前后端不同域时才填完整地址，例如 `https://api.example.com`；
- 这样避免在代码里硬编码 `127.0.0.1:8084`。

## 3. 进入端口发送请求，怎么送到后端

这是答辩最容易被问、也最容易讲乱的一段。建议按“开发 / 生产”两条链路讲。

### Q12：前端在哪个端口？请求到底发到哪个端口？

开发环境：

```text
浏览器地址栏：http://127.0.0.1:8002
页面里 fetch： /api/notes
实际先到：    http://127.0.0.1:8002/api/notes
```

也就是说，**浏览器先访问 8002，不是直接访问 8084**。8002 上的 Vite 开发服务器收到 `/api` 后，再转发给 8084。

生产环境：

```text
浏览器地址栏：https://note.example.com
页面里 fetch： /api/notes
实际先到：    https://note.example.com/api/notes（Nginx 443）
Nginx 再转发：http://127.0.0.1:8084/notes
```

### Q13：开发环境 Vite 代理怎么工作？

配置：`frontend/note/vite.config.mjs`

```js
const API_TARGET = 'http://127.0.0.1:8084'

export default defineConfig({
  server: {
    port: 8002,
    proxy: {
      '/api': {
        target: API_TARGET,
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, '')
      },
      '/uploads': {
        target: API_TARGET,
        changeOrigin: true
      }
    }
  }
})
```

逐步说明：

1. 页面执行 `fetch('/api/notes')`；
2. 浏览器按同源规则，请求 `http://127.0.0.1:8002/api/notes`；
3. Vite 的 proxy 匹配 `/api`；
4. `rewrite` 把 `/api/notes` 改成 `/notes`；
5. 转发到 `http://127.0.0.1:8084/notes`；
6. 后端返回 JSON，Vite 原样回给浏览器。

`/uploads` 不 rewrite，因为头像 URL 本身就是 `/uploads/xxx`，后端也映射在 `/uploads/**`。

### Q14：生产环境 Nginx 怎么工作？

配置：`deploy/nginx/note.conf`

```nginx
upstream note_backend {
    server 127.0.0.1:8084;
    keepalive 16;
}

location /api/ {
    rewrite ^/api(/.*)$ $1 break;
    proxy_pass http://note_backend;

    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

location /uploads/ {
    proxy_pass http://note_backend;
}
```

逐步说明：

1. 浏览器请求 `https://域名/api/notes`；
2. Nginx 匹配 `location /api/`；
3. `rewrite` 把 `/api/notes` 改成 `/notes`；
4. `proxy_pass` 转发到 `127.0.0.1:8084/notes`；
5. Nginx 把后端响应回给浏览器。

**为什么要 rewrite？**

后端 Controller 映射的是 `/notes`、`/auth/login`，不带 `/api`；`/api` 只是前端和网关的“入口前缀”。

### Q15：为什么浏览器不直接访问 8084？

- 同源：前端和接口都在 443/8002 下，不需要 CORS；
- 安全：8084 只开在内网/本机，公网只暴露 Nginx；
- TLS：证书和 HTTPS 统一由 Nginx 处理；
- 入口统一：静态文件、`/api`、`/uploads` 都在一个域名下；
- 部署灵活：后端换机器只改 upstream，前端不用改代码。

### Q16：请求头、请求体、查询参数怎么带？

- 查询参数：`request('/notes', { params: { page: 1, size: 10 } })` → `/api/notes?page=1&size=10`；
- JSON body：`request('/notes', { method: 'POST', body: { title, content } })`；
- 认证头：`Authorization: Bearer <token>`，由 `authHeader()` 自动加；
- 上传：`FormData`，**不要手写 `Content-Type`**，让浏览器自动生成 boundary。

```js
// 上传头像（节选）
export async function upload(path, file) {
  const form = new FormData()
  form.append('file', file)

  const res = await fetch(`${BASE}${API_PREFIX}${path}`, {
    method: 'POST',
    headers: authHeader(),   // 只带 Authorization，不手写 Content-Type
    body: form
  })
  return parseResponse(res)
}
```

### Q17：请求到了 8084 之后，Spring Boot 怎么找到 Controller？

1. 内嵌 Tomcat 监听 8084，收到 HTTP 请求；
2. Spring MVC 的 `DispatcherServlet` 根据方法、路径匹配 `@RequestMapping/@GetMapping/@PostMapping`；
3. 例如 `GET /notes` 匹配 `NoteController.listNotes()`；
4. Controller 调用 Service，Service 调用 Mapper；
5. 返回值被 Jackson 序列化成 JSON。

```java
@RestController
@RequestMapping("/notes")
public class NoteController {

    @GetMapping
    public Result listNotes(@RequestParam(value = "keyword", required = false) String keyword,
                            @RequestParam(value = "page", defaultValue = "1") int page,
                            @RequestParam(value = "size", defaultValue = "10") int size,
                            @RequestHeader(value = Auth.HEADER_USER_ID, required = false) Long userId) {
        return noteService.listNotes(requireLogin(userId), keyword, null, null, false, page, size);
    }
}
```

### Q18：JwtAuthFilter 在什么时候执行？

`JwtAuthFilter` 是 Servlet 过滤器，在 `DispatcherServlet` 之前执行：

```text
Tomcat
  → JwtAuthFilter
      ├─ 白名单（登录/注册/发码/actuator/uploads）→ 直接放行
      ├─ 没有 token → 401
      ├─ token 验签失败 → 401
      └─ 验签成功 → 写入 X-User-* → 放行
  → DispatcherServlet
  → Controller
```

关键代码：

```java
// JwtAuthFilter.java（节选）
private static final List<String> WHITE_LIST = List.of(
        "/auth/register",
        "/auth/login",
        "/auth/send-code",
        "/auth/reset-password",
        "/actuator/**",
        "/uploads/**"
);

protected void doFilterInternal(HttpServletRequest request,
                                HttpServletResponse response,
                                FilterChain filterChain) throws ServletException, IOException {
    String path = request.getRequestURI().substring(request.getContextPath().length());

    if ("OPTIONS".equalsIgnoreCase(request.getMethod()) || isPublic(path)) {
        filterChain.doFilter(new IdentityRequest(request, null), response);
        return;
    }

    String token = request.getHeader(HttpHeaders.AUTHORIZATION);
    if (token == null || token.isBlank()) {
        unauthorized(response, "未登录，请先登录");
        return;
    }

    JwtUtil.Payload payload = JwtUtil.verify(token, secret);
    filterChain.doFilter(new IdentityRequest(request, payload), response);
}
```

**关键点：**

- 先删除客户端伪造的 `X-User-*`，再写回验签后的值；
- Controller 不直接解析 token，只读 `X-User-Id`、`X-User-Role`；
- 白名单路径不写身份头，所以登录接口拿不到 userId，这是故意的。

### Q19：后端响应怎么回到前端？

1. Controller 返回 `Result`；
2. Jackson 序列化成 JSON；
3. HTTP 响应经过 Nginx/Vite 原路返回；
4. 前端 `parseResponse` 读取 `res.json()`；
5. `success !== true` 抛 `ApiError`，页面 `try/catch` 显示 `errMessage`。

成功：

```json
{
  "success": true,
  "data": { "id": 1, "title": "笔记" },
  "total": null,
  "errMessage": null
}
```

分页：

```json
{
  "success": true,
  "data": [ ... ],
  "total": 37,
  "errMessage": null
}
```

业务失败：

```json
{
  "success": false,
  "data": null,
  "total": null,
  "errMessage": "邮箱或密码不正确"
}
```

## 4. 核心功能的代码块

这一节建议挑 3～4 个讲，不要从头读到尾。每个代码块都先说“这段解决什么问题”。

### 4.1 登录：Controller → Service → JWT

Controller：`server/.../user/controller/AccountController.java`

```java
@PostMapping("/auth/login")
public Result login(@RequestBody LoginReq req) {
    LoginRes res = userService.login(req.email(), req.password());
    return Result.ok(res);
}
```

Service：`server/.../user/service/impl/UserServiceImpl.java`

```java
@Override
public LoginRes login(String email, String password) {
    String mail = normalizeEmail(email);
    if (mail.isEmpty()) {
        throw new BusinessException("请输入邮箱");
    }

    NoteUser user = userMapper.findByEmail(mail);
    if (user == null) {
        // 不区分「邮箱不存在」与「密码错误」，避免被用来枚举账号
        throw new BusinessException("邮箱或密码不正确");
    }

    if (!Boolean.TRUE.equals(user.getEnabled())) {
        throw new BusinessException("该账号已被禁用，请联系管理员");
    }
    if (!passwordEncoder.matches(password == null ? "" : password, user.getPassword())) {
        throw new BusinessException("邮箱或密码不正确");
    }

    String token = JwtUtil.sign(user.getId(), user.getEmail(), user.getRole(),
            jwtSecret, jwtTtlSeconds);

    writeUserLog(user.getId(), "登录", "邮箱登录成功");
    return new LoginRes(token, profile(user.getId()));
}
```

讲解要点：

- 密码用 BCrypt `matches`，数据库不存明文；
- 账号不存在和密码错误返回同一句，防止枚举；
- 禁用账号单独提示，符合需求；
- token 的 `sub` 放邮箱，`uid` 放用户 ID，`role` 放角色；
- 登录成功写操作日志。

### 4.2 JWT 过滤器：所有受保护接口的统一入口

```java
// common/security/JwtAuthFilter.java（节选）
String token = request.getHeader(HttpHeaders.AUTHORIZATION);
if (token == null || token.isBlank()) {
    unauthorized(response, "未登录，请先登录");
    return;
}

JwtUtil.Payload payload = JwtUtil.verify(token, secret);
filterChain.doFilter(new IdentityRequest(request, payload), response);
```

`JwtUtil.verify` 做了：

- 校验三段式格式；
- 用同一个 secret 做 HMAC-SHA256；
- `MessageDigest.isEqual` 定长比较，避免时序侧信道；
- 解析 payload，校验 `exp` 过期；
- 取出 `uid`、`sub`、`role`。

**可以主动说：**

> 这里没有用 Spring Security 的完整过滤器链，只用了 `spring-security-crypto` 的 BCrypt，JWT 自己实现。好处是轻，缺点是缺少现成的会话管理、CSRF、方法级权限，后续可以换。

Controller：

Mapper：`server/src/main/resources/mapper/NoteMapper.xml`

```xml
<sql id="noteListConditions">
    <where>
        n.`user_id` = #{userId}
        AND n.`deleted` = #{deleted}
        <if test="keywordPattern != null">
            AND (n.`title` LIKE #{keywordPattern} OR n.`content` LIKE #{keywordPattern})
        </if>
        <if test="folderId != null">
            AND n.`folder_id` = #{folderId}
        </if>
        <if test="tagIds != null and tagIds.size() > 0">
            AND EXISTS (SELECT 1
                        FROM `note_tag_rel` tr
                        WHERE tr.`note_id` = n.`id`
                          AND tr.`tag_id` IN
                        <foreach item="tid" collection="tagIds" open="(" separator="," close=")">
                            #{tid}
                        </foreach>)
        </if>
        <if test="unfiled">
            AND n.`folder_id` IS NULL
        </if>
    </where>
</sql>

<select id="selectNotes" resultType="Note">

    FROM `note` n
    <include refid="noteListConditions"/>
    ORDER BY n.`updated_at` DESC, n.`id` DESC
    LIMIT #{limit} OFFSET #{offset}
</select>
```

讲解要点：

- 第一条条件就是 `n.user_id = #{userId}`，从 SQL 层防越权；
- `deleted` 区分正常/回收站；
- `<if>` 做动态条件，避免写 5 个 Mapper 方法；
- 标签用 `EXISTS` 子查询，避免 JOIN 后分页重复；
- `#{}` 是预编译占位符，防 SQL 注入；
- 分页 `LIMIT/OFFSET`，Service 里把 `size` 限制在 1–100。

### 4.4 新建笔记：事务保证“笔记 + 标签”一起成功

- `userId` 来自过滤器，不信任前端传的 userId；

### 4.5 AI 总结：先调模型，成功后再原子扣额度

```java
// ai/service/impl/AiServiceImpl.java（节选）
String summary = callModel(endpoint, apiKey, model, title, input);

// 原子扣减：把「额度 > 0」写进 WHERE，避免并发下扣成负数
int deducted = aiMapper.deductQuota(userId);
if (deducted == 0) {
    throw new BusinessException("AI 额度已用完，请联系管理员分配");
}

NoteAiSummaryRecord record = new NoteAiSummaryRecord();
record.setNoteId(noteId);
record.setUserId(userId);
record.setSourceSnippet(snippet);
record.setSummary(summary);
record.setQuotaCost(QUOTA_COST);
aiMapper.insertSummaryRecord(record);
```

对应 SQL 的核心思想：

```sql
UPDATE note_user
SET ai_quota = ai_quota - 1
WHERE id = #{userId}
  AND ai_quota > 0
```

讲解要点：

- 不是“先查额度再减”，而是把条件写进 `UPDATE`，看受影响行数；
- 并发下不会扣成负数；
- 但当前是“模型调用成功后扣费”，如果模型成功、扣费/落库失败，存在额度与成本不一致的窗口，这是已知限制，可以主动说。

### 4.6 统一返回与全局异常

`Result`：

```java
public class Result {
    private Boolean success;
    private String errMessage;
    private Object data;
    private Long total;

    public static Result ok(Object data) {
        return new Result(true, null, data, null);
    }

    public static Result fail(String errMessage) {
        return new Result(false, errMessage, null, null);
    }
}
```

`GlobalExceptionHandler`：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    @ResponseStatus(HttpStatus.OK)
    public Result onBusiness(BusinessException e) {
        log.info("业务拒绝：{}", e.getMessage());
        return Result.fail(e.getMessage());
    }

    @ExceptionHandler(DataAccessException.class)
    @ResponseStatus(HttpStatus.OK)
    public Result onDataAccess(DataAccessException e) {
        log.error("数据库异常", e);
        return Result.fail("数据操作失败，请稍后重试");
    }

    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.OK)
    public Result onUnexpected(Exception e) {
        log.error("未预期异常", e);
        return Result.fail("服务异常，请稍后重试");
    }
}
```

**老师可能问：为什么业务异常也返回 HTTP 200？**

回答：

> 这是前后端约定的“信封模式”：HTTP 200 表示请求被后端正常处理，业务是否成功看 `success`。好处是前端只解析一种结构，不用区分 400/500 的多种错误页。代价是不符合严格 REST 语义；如果重做，我会让业务错误用 4xx，并在前端统一映射，或者保留 200 + 业务码。

## 5. 前后端怎么协作

### Q20：接口契约是什么？

- 路径：前端 `api/index.js` 写 `/auth/login`、`/notes`，`request.js` 统一加 `/api`；
- 方法：GET 查询、POST 新建/动作、PUT 更新、DELETE 删除；
- 请求：JSON body 或 query，字段用 camelCase；
- 响应：`{ success, data, total, errMessage }`；
- 时间：ISO 8601 字符串；
- 认证：`Authorization: Bearer <token>`；
- 上传：`multipart/form-data`，字段名 `file`。

### Q21：登录之后，前后端怎么保持登录态？

1. 登录接口返回 `token` + `user`；
2. 前端 `userStore.login` 把 token 存 `localStorage`；
3. 之后每次请求 `request.js` 自动加 `Authorization`；
4. 后端过滤器验签，写 `X-User-*`；
5. 刷新页面时，路由守卫用 token 调 `/user/profile` 恢复用户信息；
6. token 过期/无效，接口返回 401，前端抛 `ApiError`，页面回登录。

**主动说清楚：**

> 当前没有 refresh token，也没有全局自动跳转；401 由页面/守卫处理。JWT 是无状态的，退出登录只是前端删 token，服务端没有会话可清。

### Q22：错误怎么处理？

- 网络错误：`fetch` 抛异常 → `ApiError('网络请求失败')`；
- HTTP 非 2xx：`parseResponse` 抛 `ApiError`；
- 业务失败：HTTP 200 + `success:false`，同样抛 `ApiError`；
- 页面只 `try/catch`，用 `errMessage` 提示；
- 未知异常统一由 `GlobalExceptionHandler` 兜底，不把 SQL 细节返回给前端。

### Q23：跨域怎么处理？

- 开发：前端 8002，通过 Vite proxy 转发到 8084，浏览器看到的是同源 `/api`，不需要 CORS；
- 生产：前端和 `/api` 都在同一个域名 443 下，由 Nginx 反代，同样不需要 CORS；
- 只有前后端不同域时才需要后端加 `Access-Control-Allow-Origin`，或者继续用网关/Nginx 同源代理。

### Q24：文件上传怎么协作？

- 前端 `upload()` 用 `FormData`，字段名 `file`；
- 不手写 `Content-Type`，让浏览器带 boundary；
- 后端 `@RequestParam("file") MultipartFile` 接收；
- 限制 2MB，校验扩展名、魔数、`ImageIO` 可解码、尺寸；
- 服务端生成文件名，不信任客户端文件名；
- 返回可访问的 `/uploads/xxx` URL。

### Q25：前后端联调的顺序？

1. 先定接口：路径、方法、入参、出参；
2. 后端用 curl/Postman 调通；
3. 前端 `api/index.js` 加方法；
4. 页面接 API，处理 loading/empty/error；
5. 看浏览器 Network：URL、状态码、请求头、响应体；
6. 有问题先判断是代理/路径，还是后端业务。

## 6. 数据库与安全

### Q26：数据库有哪些表？索引怎么设计的？

10 张表：

`note_user`、`note`、`note_tag`、`note_tag_rel`、`note_folder`、`note_ai_summary_record`、`note_ai_config`、`note_system_announcement`、`note_user_operation_log`、`note_admin_operation_log`。

关键索引：

- `note_user`：`uk_user_email`、`idx_user_username`；
- `note`：`idx_note_user_deleted_updated(user_id, deleted, updated_at)` 支撑列表；
- `note`：`idx_note_folder(user_id, folder_id, deleted)` 支撑文件夹筛选；
- `note_tag_rel`：联合主键 `(note_id, tag_id)` + `idx_rel_tag(tag_id)`；
- `note_ai_summary_record`：`idx_ai_user_created`、`idx_ai_note`；
- 日志表按 `user_id/admin_id + created_at`、`type` 建索引。

### Q27：怎么防止用户 A 看到用户 B 的笔记？

三层：

1. 过滤器保证请求有合法身份，Controller 从 `X-User-Id` 拿 userId；
2. Service 先校验归属，例如 `requireNoteVo(userId, noteId)`；
3. SQL 的 `WHERE` 带 `user_id`，例如 `WHERE id = #{noteId} AND user_id = #{userId}`。

**不要只答“前端不显示别人的 ID”**，那不算安全。

### Q28：怎么防 SQL 注入？

- MyBatis 全部用 `#{}`，预编译参数；
- 不拼接用户输入；
- 动态排序/表名这种必须拼接的场景，用白名单，不用 `${}`；
- LIKE 的 `%`、`_` 做转义，避免用户搜 `100%` 时全表匹配；
- 数据库账号最小权限。

### Q29：密码怎么存？

- BCrypt 哈希，数据库不存明文；
- 登录用 `passwordEncoder.matches(raw, hash)`；
- 不返回密码字段；
- 种子账号首次登录后要求修改。

### Q30：验证码怎么实现？

- 内存 `Map` 保存：邮箱 + 用途 → 验证码、过期时间、尝试次数、发送时间；
- 5 分钟有效、60 秒冷却、最多 5 次；
- 用途隔离：注册、找回密码、换绑旧邮箱、换绑新邮箱；
- 单实例够用；多实例要迁 Redis。

### Q31：头像上传怎么防恶意文件？

- 限制 2MB；
- 扩展名白名单；
- 读文件头魔数；
- `ImageIO.read` 能解码才算图片；
- 限制宽高；
- 服务端生成随机文件名；
- 上传目录不在 classpath，避免被当代码执行。

### Q32：XSS 怎么防？

- Vue 模板默认转义；
- Markdown 预览先 HTML 转义，再渲染允许的语法；
- 链接只允许 `http(s)`、`mailto:`、站内路径、锚点；
- 后端返回 JSON，不拼接 HTML；
- 仍需注意：token 在 `localStorage`，一旦 XSS 可被读取，后续可改 HttpOnly Cookie。

### Q33：哪些地方用了事务？

- 新建笔记 + 绑定标签；
- 更新笔记 + 重绑标签；
- 清空回收站（先删摘要，再删笔记）；
- 永久删除（先删摘要，再删笔记）；
- 移动文件夹、恢复等单表操作也标了 `@Transactional`，保证异常回滚。

### Q34：分页怎么实现？深分页怎么办？

- 先 `COUNT(*)` 查 total，再 `LIMIT #{limit} OFFSET #{offset}` 查当前页；
- `size` 限制 1–100，防止一次拉 10 万条；
- 页码非法归 1，避免负数 OFFSET；
- 深分页 `OFFSET` 很大时会慢，改进可以用“上一页最后一条的 id/updated_at”做游标分页。

## 8. 难点、亮点、不足

### Q39：这个项目你认为最难的地方是什么？

挑 2～3 个说，不要全说：

1. **认证链路统一**：JWT 过滤器要处理白名单、伪造身份头、过期、401 响应，还要让 Controller 只读可信头；
2. **越权防护**：所有用户数据 SQL 都带 `user_id`，Service 还要先校验归属，避免“改个 id 就能看别人笔记”；
3. **AI 额度并发**：用 `UPDATE ... WHERE ai_quota > 0` 的受影响行数判断，避免先查后扣导致负数；
4. **前端请求收敛**：把 URL、token、错误、上传统一到 `request.js`，页面不重复写。

### Q40：项目亮点怎么说？

- 单体但不混乱：按 user/core/ai/admin 分包，边界清晰；
- 认证在过滤器统一做，业务代码不重复解析 token；
- 统一响应 + 全局异常，前端只处理一种错误；
- 越权防护落到 SQL，不依赖前端隐藏；
- AI 额度原子扣减；
- 一键脚本降低部署门槛；
- 前端请求层/路由守卫/状态管理分层清楚。

### Q41：项目有哪些不足？

主动说，显得客观：

- JWT 没有 refresh/吊销，禁用用户后 token 到期前仍有效；
- 验证码在单机内存，多实例要 Redis；
- AI 先调模型后扣额度，存在失败窗口；
- 没有自动化测试和 CI；
- 没有接口限流、防刷；
- token 存 `localStorage`，XSS 风险；
- 深分页用 OFFSET，数据量大时慢；
- AI 密钥明文存库；
- 前端列表请求没有取消机制，快速切换筛选可能出现旧响应覆盖。

### Q42：如果重做，你会怎么改？

- 验证码、token 黑名单迁 Redis；
- AI 额度改成“预占 → 成功确认 → 失败释放”；
- 接口加限流、幂等；
- 引入单元测试/集成测试和 CI；
- token 改 HttpOnly Cookie + CSRF 防护，或短期 access + refresh；
- 深分页改游标；
- 需要多服务时再拆，不为了微服务而微服务。

| 文件上传怎么防？ | 大小、扩展名、魔数、ImageIO、服务端文件名 |
| 跨域怎么处理？ | 开发 Vite 代理、生产 Nginx 同源，不需要 CORS |
| 怎么部署？ | `mvnw package` 一个 jar + Nginx + MySQL，脚本一键启动 |
| 最大不足？ | JWT 无吊销、验证码在内存、AI 扣费窗口、没有自动化测试 |

## 11. 答辩时的表达建议

1. **先结论，再展开**：老师问“怎么封装”，先说“分请求层、API 层、状态层、路由层四层”，再挑一层讲代码。
2. **用链路代替堆概念**：不要背“高内聚低耦合”，直接说“浏览器 → 8002 → Vite 去掉 /api → 8084 → 过滤器 → Controller → Mapper → MySQL”。
3. **主动说取舍**：单体 vs 微服务、JWT vs Session、HTTP 200 vs 4xx、localStorage vs Cookie；有取舍才像自己做的。
4. **不会的不要编**：可以说“这部分当前没做，我的改进方案是……”，比硬编好。
5. **代码只讲关键行**：例如 `JwtAuthFilter` 只讲白名单、验签、写身份头三件事，不要逐行念。
